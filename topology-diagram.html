Leader Discovery: BFS vs DFS

Both traversals return the same leader for every partition. When they diverge, you have a split-brain bug.

BFS (Queue — Level Order):
  • Enqueue Topic → Dequeue → Enqueue all 6 Partitions
  • Dequeue Partition 0 → Match partition_id == "0" ✓ → Return leader_broker_id = broker-0
  • Time: O(partitions + replicas) = O(18) worst case
DFS (Stack — Depth First):
  • Push Topic → Pop → Push Partitions [5,4,3,2,1,0] (reversed for correct order)
  • Pop Partition 0 → Match partition_id == "0" ✓ → Return leader_broker_id = broker-0
  • Same complexity, different visit order

Broker Failure & Automatic Reassignment

Replication Factor = 2 means each partition has 1 leader + 1 replica. On leader failure, the replica promotes.

  • Initial: Partition 0 leader = broker-0, Partition 3 leader = broker-0
  • Kill broker-0: Mark OFFLINE. Scan replicas for Partition 0 & 3.
  • Promote: Partition 0 → broker-1 (was replica). Partition 3 → broker-1 (was replica).
  • Kill broker-1: Partition 0 & 3 → broker-2.
  • Result: All 6 partitions still available. Cluster health = degraded (under-replicated), not down.

Kubernetes Headless Service Discovery

No hardcoded IPs. No load balancer. Brokers discover each other via DNS.

  • StatefulSet provides stable pod names: streamcore-broker-0, -1, -2
  • Headless Service (clusterIP: None) resolves service name directly to pod IPs
  • Each broker resolves streamcore-broker-headless.streamcore.svc.cluster.local → gets all 3 pod IPs
  • On startup, broker registers itself in cluster topology; others discover it automatically
  • Scale to 4 replicas: just kubectl scale statefulset streamcore-broker --replicas=4
